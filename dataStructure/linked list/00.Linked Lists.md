# Linked lists — cheap rewiring, expensive finding

**Mental picture:** `head → [value | next] → [value | next] → null`. Each node points to the next; nodes are not required to be adjacent in memory. Access by position requires walking from the head.

| Variant  | Links                      | Strength                                         | Cost                                                        |
| -------- | -------------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| Singly   | `next`                     | simple forward traversal, cheap head insert      | finding previous node to delete can be `O(n)`               |
| Doubly   | `prev`, `next`             | `O(1)` delete of a **known node**, bidirectional | extra pointer per node; more link updates                   |
| Circular | last `next` points to head | round-robin traversal                            | termination needs care; keep a tail pointer for `O(1)` ends |

## The pointer invariant

```text
Before: head -> A -> B -> C -> null
Delete B when A is known: A.next = B.next
After:  head -> A ------> C -> null
Reverse one link: save next BEFORE current.next = previous
```

If the caller only supplies a _value_, locate it first (`O(n)`); `O(1)` deletion describes the **rewiring step**, not the entire operation. In a singly list, deleting the tail requires the predecessor. A dummy/sentinel head simplifies deleting the original head.

| Operation                               | Singly (head only)      | Singly with tail                | Doubly with head + tail    |
| --------------------------------------- | ----------------------- | ------------------------------- | -------------------------- |
| Index lookup / value search             | `O(n)`                  | `O(n)`                          | `O(n)`                     |
| Prepend / remove head                   | `O(1)`                  | `O(1)` (update tail if emptied) | `O(1)`                     |
| Append                                  | `O(n)`                  | `O(1)`                          | `O(1)`                     |
| Remove tail                             | `O(n)`                  | `O(n)`                          | `O(1)`                     |
| Remove known node _with required links_ | `O(1)` with predecessor | `O(1)` with predecessor         | `O(1)` with node reference |

Space `O(n)` plus link(s) per node; sequential scans usually have worse cache locality than arrays. JS arrays are often the simpler and faster default in practice.

## Four interview patterns

1. **Reverse:** `prev = null`, advance `current` while saving `next`; make `current.next = prev`. `O(n)` time / `O(1)` extra space.
2. **Middle / cycle:** slow moves 1, fast moves 2. If they meet in a finite cyclic list there is a cycle; if fast reaches null, there is none. `O(n)` / `O(1)`.
3. **Nth from end:** move lead pointer `n` nodes ahead, then move lead and follow together. A dummy head handles removal of the first node; validate `n` in real APIs.
4. **LRU:** `Map<key,node>` finds nodes; doubly linked list tracks recency so move-to-front and evict-tail are `O(1)` average, ignoring GC/locking/persistence. Both structures are essential.

**Architecture lens:** LRU is a local eviction policy, not a complete cache design: choose capacity units (entries or bytes), TTL, concurrency, persistence and invalidation separately. Circular lists can model round-robin schedules; an array with modulo indexing may be simpler for a small fixed roster.
