# TypeScript Variable Declarations: `var`, `let`, `const`

`let` and `const` are block-scoped declarations that fix long-standing footguns in `var`'s function-scoping/hoisting model.

## `var` declarations — the problems

### 1. Function-scoped, not block-scoped
```typescript
function f(shouldInitialize: boolean) {
    if (shouldInitialize) {
        var x = 10;
    }
    return x; // Accessible here even though declared inside the if-block!
}
```
`var` ignores block boundaries (`if`, `for`, `{}`) — it's scoped to the entire enclosing function.

### 2. Re-declaration is allowed silently
```typescript
function f(x: number) {
    var x;       // no-op, same variable
    var x;       // still fine

    if (true) {
        var x;   // still the SAME x — no new scope created
    }
}
```
This makes bugs easy to introduce in large functions where a variable name gets reused by accident.

### 3. The classic closure-in-a-loop interview question
```typescript
for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 0);
}
// Logs: 3, 3, 3 — all callbacks share the SAME `i` (function/global scoped)

for (let j = 0; j < 3; j++) {
    setTimeout(() => console.log(j), 0);
}
// Logs: 0, 1, 2 — `let` creates a NEW binding of `j` per iteration
```
> One of the most common TypeScript/JavaScript interview questions — know the *why*: `let` in a `for` loop captures a fresh binding per iteration; `var` shares one binding across all iterations/closures.

## `let` and `const`
- **Block-scoped**: only accessible within the nearest enclosing `{}`.
- **Temporal Dead Zone (TDZ)**: accessing a `let`/`const` before its declaration throws a `ReferenceError` (unlike `var`, which is hoisted and initialized to `undefined`).
```typescript
console.log(a); // ReferenceError (TDZ)
let a = 5;

console.log(b); // undefined (hoisted, not an error)
var b = 5;
```
- **No re-declaration** in the same scope (`let x; let x;` → compile error).
- **`const`**: must be initialized at declaration and **cannot be reassigned** — but this is shallow: object/array *contents* referenced by a `const` binding can still be mutated.
```typescript
const arr = [1, 2, 3];
arr.push(4);      // OK — mutating contents, not reassigning the binding
// arr = [];      // Error — reassignment not allowed
```

## Destructuring

### Array destructuring
```typescript
let input = [1, 2];
let [first, second] = input;
console.log(first);  // 1
console.log(second); // 2
```

### Object destructuring (+ rest operator)
```typescript
let object = { a: "foo", b: 12, c: "bar" };
let { a, ...passthrough } = object;

let total = passthrough.b + passthrough.c.length; // 12 + 3 = 15
```

## Spread operator
The spread operator (`...`) is the **opposite** of destructuring — it expands an array/object into another array/object instead of pulling values out.
```typescript
let first = [1, 2];
let second = [3, 4];
let bothPlus = [0, ...first, ...second, 5];
// bothPlus = [0, 1, 2, 3, 4, 5]

let defaults = { width: 100, color: "white" };
let options = { ...defaults, height: 200 };
// { width: 100, color: "white", height: 200 } — later keys override earlier ones
```

## Senior best practices
1. Default to `const`; use `let` only when reassignment is truly needed.
2. Never use `var` in new code — it has no upside over `let`/`const` and reintroduces hoisting/scoping bugs.
3. Prefer destructuring for readability when pulling multiple fields from props/config/API responses.
4. Remember `const` prevents *reassignment*, not *mutation* — use `Object.freeze()` or `readonly`/`as const` for true immutability.

## Interview quick hits
- **Q: What is the Temporal Dead Zone?** The period between entering a scope and the `let`/`const` declaration being evaluated, during which accessing the variable throws.
- **Q: Why does the classic `var` vs `let` for-loop question log `3,3,3` vs `0,1,2`?** `var` has one shared binding across the whole loop; `let` creates a new binding per iteration, so each closure captures its own value.
- **Q: Does `const` make objects immutable?** No — it only prevents reassigning the variable itself; object properties/array elements can still be mutated.
