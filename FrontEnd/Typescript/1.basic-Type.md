# TypeScript Basic Types

## Basic Types Overview

### Boolean
```typescript
let isDone: boolean = false;
```

### Number
```typescript
let decimal: number = 6;
let hex: number = 0xf00d;
let binary: number = 0b1010;
let octal: number = 0o744;
```

### String
```typescript
let color: string = "blue";
let fullName: string = `John Doe`;
let sentence: string = `Hello, my name is ${fullName}`;
```

### Array
Two ways to declare arrays:
```typescript
let list: number[] = [1, 2, 3];
let items: Array<number> = [1, 2, 3];
```

### Tuple
Fixed-length array where each element may be of different type:
```typescript
let x: [string, number];
x = ["hello", 10]; // OK
// x = [10, "hello"]; // Error
```

### Enum
```typescript
enum Color {
    Red,
    Green,
    Blue
}
let c: Color = Color.Green;
```

### Any
For values that we may not know the type of at compile time:
```typescript
let notSure: any = 4;
notSure = "maybe a string";
notSure = false;
```
`any` **completely disables type checking** on that value — you get no autocomplete, no error catching, nothing. It's an escape hatch, not a type.

### Unknown (the type-safe alternative to `any`)
```typescript
let value: unknown = 4;
value = "maybe a string"; // OK to assign anything...

// ...but you CANNOT use it until you narrow it:
// value.toUpperCase(); // Error: Object is of type 'unknown'

if (typeof value === "string") {
    value.toUpperCase(); // OK — narrowed to string
}
```
> **Senior rule of thumb:** Use `unknown` instead of `any` whenever the type is genuinely not known ahead of time (e.g., `catch (e: unknown)`, JSON-parsed API data, third-party callback payloads). `unknown` forces you to prove the type before using it — `any` lets bugs slip through silently.

### Void
Absence of any type, commonly used as return type of functions:
```typescript
function warnUser(): void {
    console.log("This is a warning message");
}
```

### Null and Undefined
```typescript
let u: undefined = undefined;
let n: null = null;
```

### Never
Type that never occurs:
```typescript
function error(message: string): never {
    throw new Error(message);
}
```

### Object
Non-primitive type:
```typescript
let obj: object = {
    name: "John",
    age: 30
};
```

## Type Assertions
Two syntaxes:
```typescript
let someValue: any = "this is a string";
let strLength: number = (<string>someValue).length;
// or
let otherLength: number = (someValue as string).length;
```

## Union Types
Variable that can hold multiple types:
```typescript
let multiType: number | string;
multiType = 20;        // OK
multiType = "twenty";  // OK
// multiType = true;   // Error
```

## Type Aliases
Create custom named types:
```typescript
type Point = {
    x: number;
    y: number;
};

let center: Point = {
    x: 0,
    y: 0
};
```

## Literal Types
Specific strings and numbers as types:
```typescript
type Direction = "North" | "South" | "East" | "West";
let userDirection: Direction = "North"; // OK
// let invalid: Direction = "Invalid"; // Error
```

## Tips and Best Practices

1. Always define types when declaring variables
2. Use interfaces for object types when possible
3. Avoid `any` unless absolutely necessary
4. Use type assertions sparingly
5. Leverage TypeScript's type inference when appropriate

## Common Type Pitfalls

### Forgetting Optional Properties
```typescript
interface User {
    name: string;
    age?: number; // Optional property
}

// Both are valid
let user1: User = { name: "John" };
let user2: User = { name: "Jane", age: 25 };
```

### Mixing Up Types
```typescript
// Common mistake
let nums: number[] = ["1", "2", "3"]; // Error

// Correct way
let nums: number[] = [1, 2, 3];
// or
let strNums: string[] = ["1", "2", "3"];
```

### Function Types
```typescript
// Function type definition
type MathFunc = (x: number, y: number) => number;

let add: MathFunc = (x, y) => x + y;
let subtract: MathFunc = (x, y) => x - y;
```

## Type Narrowing
TypeScript progressively refines ("narrows") a broad type into a more specific one based on runtime checks:

```typescript
function printId(id: string | number) {
    if (typeof id === "string") {
        console.log(id.toUpperCase()); // narrowed to string
    } else {
        console.log(id.toFixed(2));    // narrowed to number
    }
}
```

Common narrowing techniques:
| Technique | Example |
|---|---|
| `typeof` | `typeof x === "string"` |
| `instanceof` | `err instanceof Error` |
| `in` operator | `"role" in user` |
| Truthiness | `if (value) { ... }` |
| Equality | `if (x === "active") { ... }` |
| Discriminated union tag | `if (shape.kind === "circle") { ... }` |

## Discriminated Unions (a must-know senior pattern)
Model different "shapes" of data with a shared **literal tag** field, then let TypeScript exhaustively narrow on it — this is the idiomatic replacement for class hierarchies/switch-on-type in many TS codebases.

```typescript
interface Circle {
    kind: "circle";
    radius: number;
}
interface Square {
    kind: "square";
    side: number;
}
type Shape = Circle | Square;

function area(shape: Shape): number {
    switch (shape.kind) {
        case "circle":
            return Math.PI * shape.radius ** 2; // shape narrowed to Circle
        case "square":
            return shape.side ** 2;              // shape narrowed to Square
        default:
            // Exhaustiveness check: if a new Shape variant is added
            // without handling it above, this line fails to compile.
            const _exhaustive: never = shape;
            return _exhaustive;
    }
}
```

## `readonly`, `as const`, and `satisfies`
```typescript
// readonly — prevents reassignment of a property
interface Point { readonly x: number; readonly y: number; }

// as const — locks a literal to its most specific type (deeply readonly + literal types)
const config = { env: "prod", retries: 3 } as const;
// config.env is type "prod", not string; config.env = "dev" is an error

// satisfies (TS 4.9+) — validates shape WITHOUT widening the inferred type
const palette = {
    red: [255, 0, 0],
    green: "#00ff00",
} satisfies Record<string, string | number[]>;
// palette.red is still inferred as number[] (not the union), so palette.red[0] works directly
```
> `satisfies` is the modern answer to "I want type-checking against a shape, but I don't want to lose the precise inferred type" — prefer it over a plain type annotation when you need both.

## Interview quick hits
- **Q: `any` vs `unknown`?** Both accept any value, but `unknown` requires narrowing before use — `any` disables type checking entirely.
- **Q: Why prefer `interface` for object shapes and `type` for unions?** Interfaces support declaration merging and give clearer error messages for object contracts; `type` is required for unions, tuples, and mapped/conditional types.
- **Q: What does `as const` do?** Infers the narrowest possible literal types and makes the structure deeply `readonly`, instead of widening to `string`/`number`.
- **Q: How do discriminated unions enable exhaustiveness checking?** Assigning the narrowed value to a variable typed `never` in the `default`/`else` branch causes a compile error if a new union member isn't handled.
