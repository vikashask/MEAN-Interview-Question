# TypeScript Modules — Fundamentals

Modules are executed within their **own scope**, not the global scope — variables, functions, classes, etc. declared in a module are **not visible outside it** unless explicitly exported. Any file containing a top-level `import` or `export` is automatically treated as a module (rather than a global script).

## Export

Any declaration (variable, function, class, type alias, interface) can be exported by adding the `export` keyword.

**Validation.ts**
```typescript
export interface StringValidator {
    isAcceptable(s: string): boolean;
}
```

**ZipCodeValidator.ts**
```typescript
export const numberRegexp = /^[0-9]+$/;

export class ZipCodeValidator implements StringValidator {
    isAcceptable(s: string) {
        return s.length === 5 && numberRegexp.test(s);
    }
}
```

### Export statements (export a name after the fact)
```typescript
class ZipCodeValidator implements StringValidator {
    isAcceptable(s: string) {
        return s.length === 5 && numberRegexp.test(s);
    }
}
export { ZipCodeValidator };
export { ZipCodeValidator as mainValidator }; // rename on export
```

### Re-export everything from another module
```typescript
export * from "./ZipCodeValidator";
```

## Import

**Import a single named export:**
```typescript
import { ZipCodeValidator } from "./ZipCodeValidator";
let myValidator = new ZipCodeValidator();
```

**Renaming imports:**
```typescript
import { ZipCodeValidator as ZCV } from "./ZipCodeValidator";
let myValidator = new ZCV();
```

**Import everything as a namespace object:**
```typescript
import * as Validators from "./ZipCodeValidator";
let v = new Validators.ZipCodeValidator();
```

**`import type` — type-only imports (TS 3.8+):**
```typescript
import type { StringValidator } from "./Validation";
```
Guarantees the import is **erased entirely** at compile time (no runtime `require`/side effect) — use it for anything imported only for its type, especially useful with `isolatedModules` build tools (esbuild/Babel/SWC) that can't otherwise tell type-only imports from value imports.

## ESM vs CommonJS — the distinction that trips people up

| | ES Modules (`import`/`export`) | CommonJS (`require`/`module.exports`) |
|---|---|---|
| Standard | Native JavaScript standard | Node.js legacy default |
| Loading | Static (analyzed at compile time) — enables tree-shaking | Dynamic (`require` can be called conditionally, anywhere) |
| `this` at top level | `undefined` | `module.exports` |
| Interop | `esModuleInterop: true` needed to `import express from "express"` cleanly against CJS packages | N/A |
| Where used | Modern bundlers, browsers, Node with `"type": "module"` | Older Node.js codebases, some npm packages |

TypeScript compiles your `import`/`export` syntax down to whichever `module` target you configure in `tsconfig.json` (`commonjs`, `esnext`, `nodenext`, etc.) — the *source* syntax can stay the same even if the emitted JS format differs.

## Why named exports are usually preferred over default exports
```typescript
// Named — refactor-friendly, better autocomplete, consistent name everywhere
export class UserService {}
import { UserService } from "./user-service";

// Default — the importer can name it ANYTHING, which hurts consistency & searchability
export default class UserService {}
import Whatever from "./user-service"; // legal, but inconsistent across a codebase
```
> Senior guidance: prefer **named exports** for most modules (services, utilities, components); reserve `export default` for cases with an unambiguous single primary export (e.g., a React page component).

## Interview quick hits
- **Q: What makes a `.ts` file a "module" instead of a global script?** Having at least one top-level `import` or `export` statement.
- **Q: Why prefer `import type` for type-only imports?** It's guaranteed to be erased at compile time with no runtime footprint, and plays well with single-file transpilers (`isolatedModules`).
- **Q: Static vs dynamic module loading — ESM vs CommonJS?** ESM imports are statically analyzable (enabling tree-shaking and dead-code elimination); CommonJS `require` is dynamic/runtime, which bundlers can't optimize as aggressively.
- **Q: When would you use `export default` vs named exports?** Default for a single obvious "main" export (e.g., a page/route component); named exports for everything else, for consistency and better refactoring/autocomplete support.
