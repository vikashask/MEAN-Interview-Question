# TypeScript Type Compatibility (Structural Typing)

## The core idea
TypeScript uses **structural typing** (a.k.a. "duck typing"): *"if it walks like a duck and quacks like a duck, it's a duck."* Compatibility is based on the **shape** of a type, not on its declared name (unlike nominal typing in Java/C#).

```typescript
interface Named {
    name: string;
}

class Person {
    name: string = "";
}

let p: Named;
p = new Person(); // OK — Person has all the members Named requires
```

> Biggest mental-model shift coming from Java/C#: **two unrelated types are compatible if their shapes match** — there's no `implements` requirement.

## Excess property checks (the exception)
Structural typing normally allows extra properties, **except** when assigning an **object literal directly** — TS then applies a stricter check to catch typos.

```typescript
interface Config { color: string; }

function setup(c: Config) {}

setup({ color: "red", colr: "blue" }); // Error: excess property 'colr' (likely a typo)

const obj = { color: "red", colr: "blue" };
setup(obj); // OK — no literal check, structural typing applies fully
```

## Function compatibility
A function type is compatible with another if:
1. It has the **same or fewer required parameters**, and
2. Each parameter type is compatible, and
3. The **return type** is compatible.

```typescript
type Handler = (a: number, b: number) => void;

const h1: Handler = (a) => {};        // OK — fewer params allowed
const h2: Handler = (a, b, c) => {};  // Error — can't require MORE params
```

This is why callbacks like `arr.forEach((item) => ...)` work even though `forEach` technically passes `(item, index, array)`.

## Enum compatibility
Numeric enums are compatible with `number`; enums from different declarations are **not** compatible with each other, even with identical values.

```typescript
enum Status { Active, Inactive }
enum Level { Low, High }

let s: Status = Status.Active;
// s = Level.Low; // Error — different enum types, not interchangeable
```

## Generics compatibility
Generics are compatible if their **structure after substitution** matches — not the type parameter name.

```typescript
interface Empty<T> {}
let x: Empty<number>;
let y: Empty<string>;
x = y; // OK — with no members using T, the shapes are identical
```

## Interview quick hits
- **Q: Structural vs nominal typing — which does TS use?** Structural.
- **Q: Why does an object literal fail but a variable of the same shape succeed?** Excess property checks only apply to literals assigned directly, to catch typos while still allowing normal structural flexibility elsewhere.
- **Q: Can a function with fewer parameters be assigned to a type expecting more?** Yes — fewer (or equal) parameters are always compatible; more are not.
